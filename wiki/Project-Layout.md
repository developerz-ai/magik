# Project layout

**Status:** the **generated app** layout is `Planned — not implemented`. `magik new` does not exist,
so nothing has ever emitted this tree. The **framework repo** layout is real and you can `ls` it.
`As of 2026-08-26`.

The directory layout is part of the product, not a suggestion. Magik is opinionated about *where
things live* for the same reason it is opinionated about the DSL: a tree whose shape you can predict
is a tree an agent can generate into without guessing, and a tree a human can read without a tour.

Two layouts live on this page. Part 1 is an app built *with* Magik — the canonical one, the one
[`dummy/`](../dummy/) follows. Part 2 is the repository that *is* Magik.

## Part 1 — a generated Magik app

### The naming rule, both directions

**One predictable mapping from filename to declaration.** An agent generating code never has to guess
a path, and a reader never has to search for where something lives.

| Declaration | File | Rule |
|---|---|---|
| `model :Invoice` | `app/models/invoice.rb` | constant → `snake_case`, singular |
| `model :LineItem` | `app/models/line_item.rb` | multi-word constants keep their word boundaries |
| `screen :Invoices` | `app/screens/invoices.rb` | screens are plural when they list, singular when they show one |
| `screen :InvoiceDetail` | `app/screens/invoice_detail.rb` | — |
| `component :MoneyCell` | `app/components/money_cell.rb` | — |
| `layout :App` | `app/layouts/app.rb` | one file per shell. `magik new` generates `:App` |
| `policy :Invoice` | `app/policies/invoice.rb` | one policy per model, named for the model it guards |
| `action :mark_paid` | `app/actions/mark_paid.rb` | actions are already `snake_case` symbols; the filename is the symbol |
| `job :SendInvoiceEmail` | `app/jobs/send_invoice_email.rb` | — |
| `channel :invoice_updates` | `app/channels/invoice_updates.rb` | — |
| `ledger :Receivables` | `app/ledgers/receivables.rb` | — |
| `flow :Onboarding` | `app/flows/onboarding.rb` | — |
| `admin_panel :Invoice` | `app/admin/invoice.rb` | named for the model the panel projects |
| `migrate :CreateInvoices` | `db/migrations/002_create_invoices.rb` | the numeric prefix orders them; the rest is the constant |
| `test :Invoices` | `test/screens/invoices_test.rb` | the test tree mirrors `app/`, plus `_test` |

Reading it the other way is the same rule run backwards: **a file's path tells you what it declares
before you open it.** `app/actions/void_invoice.rb` declares `action :void_invoice` and nothing else.

**One declaration per file.** A file under `app/actions/` that declares two actions, or an action and
a model, is a convention violation the checker is meant to catch (`MAGIK_CHECK_FILE_MULTIPLE_DECLARATIONS`,
`MAGIK_CHECK_DECLARATION_MISPLACED` — see [Error codes](Error-Codes.md)).

### What each directory is for, and what it must not hold

| Directory | Holds | Must not hold | Why |
|---|---|---|---|
| `app/models/` | field declarations, validations, associations, scopes | mutations, HTTP concerns, rendering | a model describes data and its shape. It does not act |
| `app/screens/` | layout, composition, `state` declarations | SQL, `Sequel` calls, mutations | **a screen never queries the database directly** — it names a `state`, and the state is a scope the model owns |
| `app/components/` | pure UI, driven by `prop`s | data access of any kind | a component that queries is a screen wearing a disguise |
| `app/layouts/` | the shell: navigation, `topbar`, `content` slot, responsive rules | `state` declarations, business logic | a layout wraps a screen. It does not fetch what the screen shows |
| `app/policies/` | `default :deny` and one `can` block per verb | queries, I/O, anything not a pure predicate | **authorization is decided in exactly one place.** A `live` screen re-evaluates a predicate per subscriber per change, so a query here is a round trip per row per open socket |
| `app/actions/` | the mutation, its validation, its guards | rendering markup, long-running work | **an action is the only thing that mutates.** If a screen changed data, mutation would have two homes |
| `app/jobs/` | async work, retries, schedules | request-scoped assumptions | **a job is the only thing that runs async.** Async work started anywhere else is untracked and unretryable |
| `app/channels/` | subscriptions, broadcasts | business logic | a channel routes events. It does not decide them |
| `app/ledgers/` | accounts, entries, balance guards | anything that is not money movement | **a ledger is the only thing that moves money.** A `balance` column updated by an action is exactly the bug double-entry exists to prevent |
| `app/flows/` | ordered steps and their state | the work each step does | a flow sequences actions; it does not reimplement them |
| `app/admin/` | `admin_panel` declarations: `list`, `show`, `form` | a second write path | **admin actions are the app's actions.** An inline mutation is refused |
| `app/api/` | resources, serializers, auth strategy | duplicated business logic | an API resource calls the same action a screen does |
| `app/webhooks/` | signature verification, event mapping | the handling itself | a webhook hands off to an action or a job |
| `db/migrations/` | hand-written, append-only migrations | edits to already-applied migrations | a migration that changed after it ran is a schema nobody can reproduce |
| `config/` | composition, backends, environments | business logic | if it decides *what the app does*, it belongs in `app/` |
| `test/` | one test file per declaration | fixtures files | factories are **inferred** from field types — see [Testing](Testing.md) |
| `public/` | files served byte-for-byte | anything compiled | there is no asset pipeline and no build step |

### Separation of concerns, concretely

The five rules that do the real work. Each one has exactly one directory, and that is not a
coincidence — it is the mechanism.

| Rule | Enforced by | Fails with |
|---|---|---|
| A screen never queries the database directly | screens can only read declared `state`; a `Sequel` dataset built inside a `body` block is refused | `MAGIK_RENDER_SCREEN_DIRECT_QUERY` |
| An action is the only thing that mutates | writes outside an `action` body are refused at boot | `MAGIK_ACTION_MUTATION_OUTSIDE` |
| A job is the only thing that runs async | spawning a fiber or thread outside a `job` is refused | `MAGIK_JOBS_ASYNC_OUTSIDE` |
| A ledger is the only thing that moves money | a `:money` field written outside a ledger entry is refused | `MAGIK_LEDGER_MONEY_OUTSIDE` |
| A policy is the only thing that authorizes | every surface reaching a model names a verb; there is no per-surface check to write, and no surface may skip the declaration | `MAGIK_POLICY_UNDECLARED` |

These are **boot-time guardrails**, not lint warnings. The whole point is that the layout and the
enforcement agree: if the rule can be broken without moving a file, the rule is decoration. See
[`docs/idea/03-guardrails.md`](../docs/idea/03-guardrails.md).

### Generated versus hand-written

Nothing hand-written sits next to something the framework owns. You never have to ask "is it safe to
edit this file".

| Path | Owner | Committed | Editing it |
|---|---|---|---|
| `app/**` | you | yes | yes — this is your app |
| `config/**` | you | yes | yes |
| `db/migrations/**` | **you**, hand-written | yes | only before it has run anywhere |
| `db/schema.rb` | **the framework**, generated | yes — it is the reproducible truth | **never.** Change a migration and regenerate |
| `db/seeds.rb` | you | yes | yes |
| `locales/**` | you, with generated stubs for missing keys | yes | yes |
| `test/**` | you, scaffolded by `magik generate` | yes | yes |
| `public/htmx.min.js` | the framework, vendored | yes | never — it is replaced on upgrade |
| `bin/setup`, `bin/check` | the framework, generated once | yes | yes, they are yours after generation |
| `CLAUDE.md`, `llms.txt`, `docs/FEATURE.md` | **jointly owned** — the framework and you | yes | yes, in the project block. Only the marked framework block is regenerable, by `magik generate agents --update` — [`docs/idea/09-app-scaffold.md`](../docs/idea/09-app-scaffold.md) |
| `tmp/**`, `log/**` | the framework | **no**, gitignored | never |
| `.env` | you | **no**, gitignored | yes. `.env.example` is the committed one |

The rule in one line: **generated files that are committed are never hand-edited, and hand-written
files are never overwritten by a generator.** A generator that would clobber a hand-written file is
meant to refuse with `MAGIK_CLI_WOULD_OVERWRITE` and name the file.

## How the tree scales

Two shapes, one migration between them, and a stated point at which you move.

### The small app — flat

Everything in `app/<kind>/`. No `domains/` directory at all. This is what `magik new` emits, and most
apps never leave it.

```text
app/
├── models/     invoice.rb  customer.rb  line_item.rb
├── screens/    invoices.rb  dashboard.rb
├── actions/    create_invoice.rb  mark_paid.rb
└── jobs/       send_invoice_email.rb
```

**Cost:** none. **Ceiling:** every declaration can reach every other declaration. That is fine while
everyone working on the app holds all of it in their head.

### The large app — domains

Each domain owns its own `models/`, `screens/`, `actions/` and `jobs/`, and declares what it depends
on and what it publishes. Boot-time enforcement means a domain **cannot** reach another domain's
models directly — only through the published interface or a subscribed event.

```text
domains/
├── billing/
│   ├── domain.rb            # depends_on :Identity
│   │                        # exposes :Invoice, :charge
│   │                        # publishes_events :invoice_paid
│   └── app/                 # the SAME tree as the flat one, one level in
│       ├── models/invoice.rb
│       ├── screens/invoices.rb
│       ├── actions/mark_paid.rb
│       └── jobs/sweep_overdue.rb
│   └── test/
├── identity/
│   ├── domain.rb            # exposes :User, :current_tenant
│   ├── app/models/user.rb
│   └── test/
└── reporting/
    ├── domain.rb            # depends_on :Billing
    │                        # subscribes :invoice_paid
    ├── app/screens/revenue.rb
    └── test/
app/                          # what is left: genuinely app-wide
├── components/               # shared UI
└── screens/dashboard.rb      # composes across domains
```

**A domain contains the same `app/` tree as a flat app.** That is the whole trick: a domain is a
namespace wrapped around the identical tree, not a different tree — `app/models/invoice.rb` becomes
`domains/billing/app/models/invoice.rb`, and nothing inside the file changes.

### When to move

Move when **any one** of these is true. Not before — a boundary drawn too early is a boundary drawn
in the wrong place.

| Signal | Why it is the signal |
|---|---|
| More than one team owns parts of `app/` | boundaries are an org tool before they are a code tool |
| `app/models/` passes ~25 models | past that, "which model belongs to what" stops being obvious from the list |
| Two features have started reaching into each other's models to do their work | the coupling already exists; the domain declaration makes it visible and reviewable |
| You want to extract something into its own service later | a domain boundary is the seam. Draw it while it is cheap |

### The migration is mechanical

Moving from flat to domains is `git mv` plus one file per domain. It is not a rewrite, and it is
intended to be scriptable:

```bash
mkdir -p domains/billing/app/{models,screens,actions,jobs} domains/billing/test
git mv app/models/invoice.rb        domains/billing/app/models/
git mv app/screens/invoices.rb      domains/billing/app/screens/
git mv app/actions/mark_paid.rb     domains/billing/app/actions/
git mv app/jobs/sweep_overdue.rb    domains/billing/app/jobs/
```

The path a file had inside `app/` is the path it has inside `domains/<name>/app/` — the prefix
changes and nothing else does.

Then write the one new file:

```ruby
# domains/billing/domain.rb
domain :Billing do
  depends_on :Identity
  exposes :Invoice, :charge
  publishes_events :invoice_paid, :invoice_voided
end
```

Then boot. **Every boundary you did not know you had crossed becomes a boot failure**, each naming
both domains and the exact constant:

```text
MAGIK_DOMAIN_BOUNDARY: :Reporting reads :Billing::Invoice directly
  fix: add `exposes :Invoice` to domains/billing/domain.rb, or subscribe to :invoice_paid
```

You fix them one at a time until boot is green. No declaration inside the moved files changes — a
`model :Invoice` is a `model :Invoice` whether it sits in `app/models/` or `domains/billing/app/models/`.
That is the property that makes the move mechanical, and keeping it true is a constraint on the
implementation.

Full detail: [Domains](Domains.md).

## Part 2 — this framework repository

Real. `As of 2026-08-26` most of these directories are empty or hold stubs — the framework is
unimplemented. The **shape** is fixed; the contents are not there yet.

```text
magik/
├── lib/
│   ├── magik.rb              # the module: VERSION, Error, SUBSYSTEMS, autoloads
│   └── magik/
│       ├── version.rb        # VERSION, and nothing else
│       └── <subsystem>/      # one directory per subsystem, mirroring the spec phases
├── exe/magik                 # the CLI entry point — thin, delegates to Magik::CLI
├── bin/                      # repo scripts
│   └── check                 # the gate: rubocop + rake test + doc checks
├── test/
│   └── magik/                # mirrors lib/magik/ exactly. Minitest, never RSpec
├── docs/
│   ├── README.md             # the docs index
│   ├── idea/                 # WHY — spec, thesis, DSL surface, guardrails, swaps, limits, phases
│   ├── architecture/         # HOW — conventions, module map, boundaries, error codes, testing
│   └── ops/                  # running an app for real. Recommendations only
├── wiki/                     # this reference manual — the public documentation surface
├── examples/                 # idiomatic snippets and small example apps — empty today
├── dummy/                    # the invoicing/billing demo SaaS, warts included — the canonical layout
├── .claude/                  # the agent workbench: subagent definitions and slash commands
│   ├── README.md
│   ├── agents/
│   └── commands/
├── .github/                  # CI, release, issue templates
├── llms.txt                  # the agent entry point
├── ROADMAP.md                # ten phases, thirteen build steps, version milestones
├── CHANGELOG.md
└── magik.gemspec
```

### The rules this tree encodes

| Directory | Holds | Must not hold |
|---|---|---|
| `lib/magik/<subsystem>/` | one subsystem's implementation | anything another subsystem's boundary forbids — see [`docs/architecture/02-boundaries.md`](../docs/architecture/02-boundaries.md) |
| `exe/magik` | argument handoff | logic. The binary is a shim so the CLI is testable without spawning a process |
| `test/magik/` | a test file per `lib/magik/` file, same path | fixtures unrelated to the file under test |
| `docs/idea/` | decisions and their reasoning | how the code is arranged |
| `docs/architecture/` | how the code is arranged | why a decision was made |
| `wiki/` | the reference manual for **users of the framework** | internals a user never touches |
| `dummy/` | a real app using the framework, following Part 1's layout exactly | framework code |
| `.claude/` | agent definitions and commands, committed | personal editor settings |

### One gem, many subsystems

Magik is **one gem** with subsystem modules under `lib/magik/<subsystem>/`. It is not a multi-gem
monorepo. Extraction into separate gems stays possible later; it is not promised, and no page should
imply a package boundary that does not exist.

The subsystems, mirroring the spec phases:

`core` · `cli` · `model` · `schema` · `render` · `action` · `router` · `realtime` · `jobs` ·
`ledger` · `api` · `auth` · `billing` · `admin` · `i18n` · `pwa` · `notify` · `testing` ·
`domains` · `check`

`Magik::SUBSYSTEMS` in `lib/magik.rb` is the machine-readable version of that list, and it drives
autoload registration. Read it rather than this paragraph:

```bash
ruby -Ilib -e 'require "magik"; puts Magik::SUBSYSTEMS.keys.inspect'
```

### The agent workbench

`.claude/` is where the repo keeps the tools an AI agent uses to work on it — subagent definitions and
slash commands, committed to the tree rather than kept in someone's local config. Magik is an
AI-first repo: the primary developer is an agent, and phases are landed by agents running
`/implement-phase` against [`docs/idea/06-phases.md`](../docs/idea/06-phases.md), gated by
`bin/check`. Start at [`.claude/README.md`](../.claude/README.md), and read
[`docs/idea/07-ai-first.md`](../docs/idea/07-ai-first.md) for why the repo is arranged this way.
